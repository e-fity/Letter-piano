# jianpu2letter

把「中文数字谱（简谱）」转换成「键盘字母谱（映射2）」。

输入两种，输出两种：

| 输入 | 输出 |
|---|---|
| MusicXML（标准五线谱音高） | 映射2 字母谱 XML + 中文数字谱图片 |
| 中文数字谱图片（RapidOCR + 人工审核 JSON） | 映射2 字母谱 XML + 中文数字谱图片 |

---

## 一、映射2 规则（本工具唯一采用的键位映射）

首调唱名（1=do … 7=si）对应键位：

| 音区 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 低音（八度 −1） | Z | X | C | V | B | N | M |
| 中音（八度 0） | S | D | F | G | H | J | K |
| 高音（八度 +1） | E | R | T | Y | U | I | O |

**Shift 扩展音域**（超出上表三排时）：

| 相对八度 o | 键位 |
|---|---|
| −2 | 左 Shift + 低音键 |
| −3 | 右 Shift + 低音键 |
| +2 | 左 Shift + 高音键 |
| +3 | 右 Shift + 高音键 |

> 对照（映射1，未采用）：低音 `M N B Z X C V`、中音 `A S D F G H J`、高音 `K L Y U I O`、双高音 `T R E W Q`。

## 二、其他规则（简谱判读，来自链接）

**音区判定**（最关键，最易错）：
- 数字**下方独立圆点** = 低音；数字**上方圆点** = 高音；无点 = 中音；双点 = ±2 八度。
- ⚠️ 连接数字的**下方横线（减时线）只决定时值，绝不能当低音点**。

**时值**：
- 数字下方一条减时线 = 时值减半，两条 = 再减半。
- 数字后附点 `·` = 时值 ×1.5。
- 数字后横线 `—` = 每线延长一拍。
- `0` = 休止。

**符号原位保留**：`⌒` 连音、`||:` 反复开始、`:||` 反复结束、`〔〕/〈〉` 倚音、`³` 三连音、`♯` 升号、临时升降号、重音、换气。

**简化规则**：临时升降号按「同音级自然音」简化（如升 5 按 G、临时降号按同音级自然键）。

## 三、安装

```bash
# 核心（MusicXML→字母谱 XML）无需第三方依赖
# 渲染图片需要：
pip install matplotlib numpy

# 图片 OCR（半自动草稿）需要：
pip install rapidocr-onnxruntime opencv-python
```

> OCR 引擎用 **RapidOCR**（onnxruntime 跑 PaddleOCR 模型）。实测 paddleocr 3.x
> 在 Python 3.13 + paddlepaddle 3.3.1 下初始化即崩溃（模型配置读取失败），故弃用。
> 渲染中文标题/歌词需要中文字体（如 Noto Sans CJK / 思源黑体 / 微软雅黑），
> 缺字体时数字与符号仍正常，仅中文显示为方框。

## 四、用法

```bash
# MusicXML → 字母谱 XML + 简谱图片（直接生成）
python convert.py song.musicxml -o out/

# 图片推荐使用两阶段流程。
# 第一阶段：只扫描，生成 review1/1_review.json 与 review1/ocr_overlay.png
python convert.py 1.jpg -o review1 --title 上海滩 --key C --scan-only

# 对照 ocr_overlay.png 修改 1_review.json 后，第二阶段直接构建；不重复 OCR
python convert.py review1/1_review.json -o out

# 第二张图（1=♭A 用 Ab 表示）
python convert.py 2.png -o review2 --title 屁 --key Ab --scan-only
python convert.py review2/2_review.json -o out

# 仍可一条命令直接从图片生成草稿
python convert.py jianpu.png -o out --title 曲名 --key Eb

# MusicXML 常用参数
python convert.py song.xml -o out --tonic-octave 4 --part 0 --measures-per-line 2
```

> 图片输入的**曲名和调号会自动读**：曲名取页眉**居中大字**，调号取页眉 `1=X`（如 `1=♭B`→`Bb`）。
> `--title` / `--key` 优先级最高，读不到才回退（曲名=文件名、调号=`1=C`）。用 `run_all.py` 跑时，
> 读到的 `title`/`key` **会自动写回 `piano_config.json`**（下次直接用、不再识别）；**节拍数不自动读，
> 一律写 `4/4`**；没读到的项，`title` 写占位 `"未读取标题"`、并在末尾列出 `[调号?]`/`[标题?]` 提示手填。
> 注意：调号只是谱头/XML 上的标签（`key=` 属性），**不改变识别出的字母**——简谱数字本身就是首调唱名，
> 键位只由「唱名+音区」决定。

两阶段第一步输出：
- `base_review.json` —— 可人工校正的结构化识别结果（每行带一个只读的 `text` 字段 =
  该行识别出的**字符序列**）；
- `base_jianpu.txt` —— **逐行字符序列文本**（同时打印到控制台），可直接对原谱比对；
- `ocr_overlay.png` —— 原图叠加音符编号、识别值、音区和时值；
- `binary.png` / `ocr_tokens.txt` —— 诊断辅助文件。

审核 JSON 中图上的 `L03N007` 对应同 ID 音符。通常只需修改：
`n`（数字）、`o`（音区）、`beams`（减时线数）、`dotted`、`extend`、
`slur_to_next` 与 `bar_after`。不要修改 `id` 和 `source_x`。

最终输出文件（`base` 为输入名；`_review` 后缀会自动去掉）：
- `base_letter.xml` —— 映射2 字母谱；
- `base_review.json` —— 可人工校正的结构化识别结果（**默认就出**，用户 2026-09-22 要求）。
  改完把它当输入再跑一次即可重出成品，**不重跑 OCR**：
  `python -m jianpu2letter out/7_review.json -o out`（自动去掉 `_review` 后缀）。
  它必须由 OCR 那一趟生成（含每个音的位置/时值），事后无法从 png/txt 反推；
- `base_jianpu.png` —— 重建的中文数字谱图片；
- `base_jianpu.txt` —— 逐行字符序列文本（见下）；
- `base_overlay.png` —— 原位替换图（在原谱上把数字盖成字母）；
- `base_letter.png` —— 键盘字母简谱图片：**默认不出**（用户 2026-09-22 要求，产物太多），
  要时加 `--letter-png`。字母谱的数据在 `base_letter.xml`，要在图上核对就用 `base_overlay.png`。

### 逐行「字符序列」文本（`base_jianpu.txt`）

每次转换都会额外输出一份**每行一条**的文本，用 `textscore` 的语法：

```
L01: ( 0 1 2 5 1 2 6· | 0 1 2 6 5 3 2 5 | 6· 5 3 6 | i 6 5 6- |
L02: 3 5_ 6 5 3_ 2 | 1v 6 5 3 2 - | 2· 3 5 6 6 | 3 2 1 - |
```

记号含义：数字/`0` 休止，`^` 高音点、`v` 低音点（可重复），`_` 减时线（可重复），
`·` 附点，`>` 重音记号（原谱画在数字上方的小 V），`-` 延时线（可重复），
`(` `)` 括号，`⌒` 连音，`|` `||` `:||` `||:` 小节线/终止/反复。
**未识别的音写作 `?`**（回读会报错，属预期）。

这份文本是 `textscore.py` 里 `parse_text()` 的**逆运算**（`to_text()`），所以它
**可以整个当作 `convert.py` 的输入再读回**：

```bash
python convert.py out/1_jianpu.txt -o out2 --title 曲名3
```

用途：不用看渲染图，就能逐行拿着它跟原谱核对识别结果（尤其适合"测不了声音"的场景）。

### 逐音置信度与黄底（OCR 路径）

OCR 路径会给**每个音**存一个置信度 `conf`（0..1）：

- `conf` = 该块与**它最终采用的数字**的参照字形相似度（越高越像）；
- 形状判据另有结论、且与最终结论**矛盾** → 直接压到 `0.30`（明确可疑）；
- 拿不到分数（未识别，或块尺寸不符合）→ `null`，同样按可疑处理。

**低于 `CONF_WARN`（默认 `0.70`）的音，输出图里的数字带黄底**；控制台同时打印一份
`[置信度]` 清单（`行1 音7 数字=6 置信度=0.62`）；审核 JSON 每个音也有 `conf` 字段
（只读，会一路带到重新渲染）。阈值分两处、要一起改：`ocr_jianpu.CONF_WARN`（负责算）
与 `jianpu_render.CONF_WARN`（负责画）。

> ⚠ **黄底必须是一块独立衬底，不能挂在数字自己的 `bbox` 上**：matplotlib 的
> `Text.draw()` 是**在文字自己的 zorder（3）里**顺手画 `bbox` patch 的，所以
> `get_bbox_patch().set_zorder(1)` **完全不起作用**，黄底永远盖在减时线 / 音区点 /
> 延时线（zorder=2）上面（用户 2026-09-18 报的"黄底把下划线遮住了"，当时按
> `set_zorder(1)` 修，2026-09-20 复查发现根本没生效）。
> 现行做法：`_draw_note()` 另画一个 **glyph 不可见的同款文字**（`color="none"`，
> 笔画隐去、`bbox` 照画）放在 `zorder=1`，数字本体照旧不带 `bbox`——黄底就真的
> 沉到所有墨迹下面了。

**用之前必须知道的盲区**：像《采蘑菇的小姑娘》那种 5/6 **系统性**错判，字形本来就极像，
分数会很高（0.8+），**黄底不会亮**。它擅长的是"本来就勉强过线"的音，以及帮你判断某个
`?` 该填什么。要治系统性错判得靠训练本字体模型（`train_digits.py` 生成
`digit_model.npz` 放到项目根目录；目前这个文件不存在，那条机制等于没启用）。

### 字母谱文本约定

- 大写字母 = 映射2 键位
- `_` 减时线（条数 = 时值减半次数），`·` 附点，`—` 延时线
- `0` 休止，`⌒` 连音，`|` `||` `||:` `:||` 小节线/反复
- `↑`/`↓` Shift 扩展音域（`↑`=左Shift升一层，`↑↑`=右Shift升两层，`↓`/`↓↓` 同理向下）

### 输出 XML 示例

```xml
<letter-score mapping="mapping2" key="1=Eb" meter="4/4">
  <title>世上只有妈妈好</title>
  <line n="1">||: J · H_ F H | E ⌒ J_ H_ J —</line>
  <line n="2">F H J H ⌒ F_ D_ | S ⌒ N_ H_ F_ D_ —</line>
</letter-score>
```

## 五、MusicXML → 首调的换算算法

1. 读 `<key><fifths>` 调号 → 主音（大调 `1=主音`；小调按关系大调取 `1`）。
2. 「音名步进法」：每个音符用 `octave*7 + 音名步进` 构成 diatonic index，
   主音中音锚点固定在第 4 八度（`--tonic-octave` 可调）。
   差值 `diff`：`唱名 n = diff mod 7 + 1`，`八度 o = diff // 7`。
   该算法天然忽略临时升降号（同音级简化）。
3. 由 `n, o` 查映射2得键位。
4. 时值 `duration/divisions` → `·`/`_`/`—`；`<tie>` 延音合并成 `—`。

## 六、已知局限与调优

**两条输入路径的可靠性不同，请按需选择：**

- **MusicXML → 字母谱：可靠路径（推荐）。** 纯算法换算，不依赖图像质量，
  已通过自测（`selftest.py`）。有 MusicXML 源文件时优先用它。
- **图片 OCR → 字母谱：推荐两阶段审核。** 自动扫描负责定位和初始识别，未必能
  正确判断所有音区点、减时线和连音；`scan-only` 会生成带稳定音符 ID 的叠加图与
  JSON。人工仅修正错误项后再构建，可以获得可复核的高准确率成品，而且第二阶段
  不再运行 OCR，不会因重复识别而改变结果。若跳过审核直接生成，仍只应视为草稿。

其他局限：

- **.mxl 压缩格式暂不支持**：请先导出为未压缩 `.musicxml`/`.xml`。
- **多声部**：默认取第一声部（`--part` 切换），跳过和弦内声部与倚音。
- **小调**：按关系大调处理（`1=关系大调主音`），符合简谱惯例。
- **中音1 八度锚点**：默认主音落在中央 C 八度（C4–B4），若旋律整体偏高/偏低，
  用 `--tonic-octave` 调整，否则高低音会整体错一层。
- **已知失效点（实测）**：《我的中国心》最后一行 `6 - - ) 0 3 :|| 6 - - - | 6 - - 0`
  的延时线会被少数（`6 - -` 只数出 1 条）。原因是该处数字右侧紧邻 `)`／`:||`，
  探测窗口被这类竖/弧结构挤占。其余谱面（上海滩、千年等一回、小星星、两只老虎、
  我的中国心其余各行、屁）实测正常。
  同一个窗口还有个**更凶的后果，已修**：窗口被挤到几乎为零时，`_count_extends`
  曾经**提前 `return 0`（整数）而不是元组**，而调用方写的是
  `extend, ext_xs = _count_extends(...)` → 直接
  `TypeError: cannot unpack non-iterable int object`，**整个 OCR 崩掉**（不只是少几条线）。
  《曲名3》那行 `1 - - - | 1 - ) 0` 必触发。现已改为 `return 0, []`。
- **歌词（汉字）成对重复**：《上海滩》整首每个字都出现两遍（“不不”“出出”“爱爱”）。
  根因是 OCR 在 2 倍图与 1 倍原图各跑一遍，而跨尺度去重**只做在 `tokens`（含数字块）上，
  漏了 `text_tokens`（纯汉字块 = 歌词）** → 同一行歌词进列表两份 → 逐字分配时
  `best["lyric"] += ch` 执行两遍。**已修**：给 `text_tokens` 补上去重（同块两份文本
  长度不同时留**字数多的**，如 “看不出有未” vs “看不出有未来”）。
  注意歌词是**识别阶段**的产物，改后必须重跑 `--scan-only`，重新渲染图片去不掉。
  **多段歌词已支持 2~3 段**（2026-09-29/30 改的，不再是"只取最上面那一段"）——
  第 1 段写 `lyric`、第 2/3 段写 `lyric2`/`lyric3`，两张谱图会逐段往下叠；详见 7.3 第 14 条。
- **看到 `[warn] ... 渲染失败` 不要当成「就是没生成图」。** 那是异常被捕获了，
  不是"跳过"。提示里现在带**异常类型和出错位置**，例如
  `NameError: name '_draw_parens_at' is not defined @ jianpu_render.py:286`、
  `SyntaxError: '(' was never closed @ letter_render.py:220`，结尾还会汇总
  「本次有 N 处图片渲染失败」。加 `--traceback` 打印完整调用栈。
  > 历史教训：数字谱曾因 `_draw_parens_at` 从未定义而崩，字母谱曾因一个**未闭合的括号
  > 语法错误**导致整个文件连 `import` 都过不去。两个 bug 都只表现成一句含糊的
  > `渲染失败`，于是"三样产物其实只出来两样"这个事实藏了很久。

## 七、图片识别流水线（ocr_jianpu.py）

按顺序执行，每一环都把结果作为下一环的"种子"，故越往后越准：

1. **自适应缩放**：先把整图归一到「数字高约 48px」。小字号下 OCR 与字形匹配都会
   明显退化（实测一张 600×287 的谱、数字仅 11–13px，5/6/0 的差别已糊掉）。
2. **多尺度 OCR**：在缩放图与原图各跑一遍 RapidOCR，按位置去重（≤0.6 字高的
   重叠只留一个）。小图/细字时检测器会漏掉大半，两个尺度互补。
3. **文本块处理**：
   - 含中文的块**不整条丢弃**，而是按字符位置截出数字那一段（旋律数字常与歌词
     被并成一块，整条丢会让整行消失）；
   - **跨行 token**（高度 >1.5 字高）弃用，避免把数字错配到别的行；
   - **OCR 常见误读还原**（仅用于纯文本块）：`|`/`l`→1、`S`→5、`O`/`D`→0、
     `E`→3、`T`→7、`Z`→2、`b`/`G`→6、`A`→4。含中文的块不启用（防歌词字误判）。
4. **行定位**：数字块按 y 聚类。接受一行为旋律行的条件是「块高 ≈ 数字字高（±15%）」
   或「OCR 在该行读到 ≥3 个数字」；再剔除**纯文字行**（出现 ≥2 个"纯汉字、不含数字"
   的文本块 = 歌词行/制谱行）。
5. **数字赋值**（多路并用 + 结构级收尾）：
   OCR 投票（≥2 票即采纳）→ 内孔判 0/6 → 字形相似度（与现场渲染的 0–7 参照字形
   比对，门槛 0.55）→ **字形聚类**（同类刷同一数字，并施加"投票矛盾的块不许合并"
   的约束，专门对抗 5/6/0 这类"闭合圈状"的系统性塌缩）→ 0/6 双判据定向复核。
6. **符号**：
   - **音区点**：数字上下的小圆点；低音点窗口按减时线条数下移（点画在线下方）；
   - **减时线**：数字下方、横向覆盖它的**细长横线**层数（低音点是圆点，天然排除）；
   - **附点**：数字右侧中腰的小圆点；
   - **延时线**：数字右侧独立短横段数（右端截在下一个**真音符**左边缘；纵向跨 >0.35
     字高的竖线一律忽略——那是反复记号的竖线/括号，实测会污染统计）；
   - **小节线**：细(≤0.30H)+实(fill≥0.65)+贯穿全行+不与数字重叠；数量不足时自动放宽重找；
   - **括号 `(` `)`**：优先来自 OCR 文本（含全角），并可用几何兜底（弧线高 ≥1.1 字高）；
     括号形状的块会从"数字候选"里剔除（否则被赋成数字、还会堵住延时线窗口）；
   - **反复记号 `‖:` / `:‖`**：来自 OCR 文本里的冒号**或**几何识别（相邻两条细竖线
     + 一旁的圆点；点在左=结束、点在右=开始）。归属按语义定位（`‖:` 归右侧小节、
     `:‖` 归左侧小节），只标记不展开。
7. **输出**：字母谱 XML + 中文数字谱图片 + 键盘字母简谱图片 + 逐行字符序列文本
   （`base_jianpu.txt`，见「逐行字符序列文本」一节）。

**调参**：`ocr_jianpu.py` 顶部有若干开关与常量（见下），配合 `--ocr-debug-dir`

### 7.2 渲染（输出图片）的约定

- **横向位置（字符格子）**：识别路径**不再沿用原图 x 坐标**，而是先把一行展开成
  **识别出来的字符序列**，再让**每个字符平均分配一格**、格内居中：

  ```
  (  1  .  -  -  )  |  0     ← 每个字符各占一格，格宽 = 行宽 ÷ 本行字符数
  ```

  占格的字符：数字/休止 `0`、附点 `.`、**每条**延时线 `-`、括号 `( )`、小节线 `|`。
  **不占格**的记号：减时线与音区点——它们竖着贴在数字的正上/正下方，仍画在
  数字那一列（给它们分格子会把点推到数字旁边，反而不像谱）。
  好处：行与行等长、字符间距一致、附点/每条 `-`/小节线/括号都各占自己的格子、
  不会互相挤压，也不再依赖原图检测到的竖线位置（避免检测误差造成空档）。
- **延时线 `-`**：每条**占自己的一格并在格中居中**，线长统一（0.42，格子太窄时自动缩短）。
- **音区点**：高音点在数字上方 +0.44；低音点在**减时线之下**（不与线重叠）。
- **减时线**：紧贴数字下方（−0.34），按层数向下叠。
- **小节线 / 反复 / 终止**：`|`、`‖:`、`:‖`、`‖` 用**与小节线等高同粗的竖线**绘制
  （不再用文字字符），并**取代**普通小节线（不会出现"`|` 再加 `:‖`"的重复标记）。
  小节线自己占一格，所以不会再和延时线撞在一起。
- **附点 `.`**：**自成一格**（画在数字右侧、基线稍下的位置）。
- **括号**：`(` `)` 各占自己的一格，在自己格子中间绘制；因为小节线也在自己的格里，
  `)` 天然不会越过小节线。
- **连音弧 `⌒`**：画在音符**上方**的一条弧（正弦拱），高度按链上最高的音区点自动抬高，
  免得压住高音点；**嵌套弧**（长弧上再套短弧）再按嵌套层数逐级抬高，外层在上。
  数据模型里连音**只存相邻对**（见 `_slur_chains()`），
  所以一条跨 3 个音的长弧在模型里是 2 对、画图时再拼回**一条**。
  这条弧在**数字谱图**、**字母谱图**、字母谱 XML、逐行文本上**都有**
  （字母谱图是 2026-09-18 用户追加要求，先前只画数字谱）。
- **歌词**：中文歌词**逐字**对齐到最近的音符，画在数字/字母正下方。

实现位置：`jianpu_render.py` 的 `_line_cells()`（展开字符序列）+
`_cell_positions()`（平均分配行宽）+ **`draw_cell_line()`**（按格子画一整行）。
**数字谱与字母谱共用 `draw_cell_line()`**，各自只传一个"怎么画数字/字母"的回调
——排版只留一处定义，两张图的字符位置才可能真正一一对应。
（字母谱图片原本是"按原图 x 坐标映射"，2026-09-18 按用户要求同步成同一套字符格子。）

> 修复记录：此前 `jianpu_render.render()` 在字符格子分支里调用了 `_draw_parens_at()`，
> 但该函数**从未定义** → 只要某一行含括号，整个数字谱渲染就抛 `NameError`，

### 7.3 已知限制（实测）

1. **个别数字混淆**：`5/6`、`0/6`、`5/1` 这类"字形相近"的数字，在**某些字体**上
   会偶尔错判（如《采蘑菇的小姑娘》曾把 5 整体判成 6）。根因是参照字形取自
   **系统字体**，与谱面字体不同；这类错误**只能靠人工在审核 JSON 里改几个数字**。
2. **倚音（小字号装饰音）不识别**：会被丢弃，导致该音缺失（如《枉凝眉》第一行）。
   需要"倚音识别"是另一项功能。
3. **行首与数字粘连的括号**（如《枉凝眉》第一个 `(`）认不出——它不是一个独立弧线。
4. **延时线在"音符稀疏的行"会少数（2026-09-22 已修）**。旧实现把扫描窗口右端硬卡在
   `x_end = 数字右缘 + 6.0H`：一行里音符越稀，音与音之间的 `-` 总长越长，撞上限就被截断，
   截断点之后**根本没扫**。实测《我的中国心》(`4.png`) 末行音@1212 的窗口恰好 `宽5.9H`

     > **教训：加了新维度就要检查所有读这个维度的地方**——我只改了写入端和 JSON，
     > 漏了唯一真正画线的那处。
     > ⚠ **同一段音上只留一条弧**（2026-09-18 再修）：细弧二值化后常**断成几截**，
     > 几个连通块会都映射到**同一段音**上 → 画出**两条重合的弧**（用户报的
     > "一个字符上面有 2 个弧"）。现在按「音区间」去重，只留先到的那条；
     > `[slur]` 日志也带上了**弧编号**（`→ 弧#3 连音 2 个音（音9..音10）`），
     > 便于核对"同一段音是不是被分了两条"。
     > ⚠ **编号要 `append`、不能覆盖**（2026-09-20 修）：**嵌套弧**（长弧 A-B-C 上面
     > 再套一条短弧 B-C）会在**同一个音**上留下**两个**编号——实测《上海滩》行3 的
     > `x=991 宽3.3H（音7..音9）` 与 `x=1058 宽1.9H（音8..音9）`。原来写的是
     > `notes[i]["slur_start"] = [slur_id]`（**赋值**），后处理的短弧把音8 上长弧的
     > 编号顶掉了 → 长弧的第二对（音8,音9）配不上号，画出来是"两条各跨 2 个音的弧"，
     > 而不是"一条跨 3 个音 + 一条嵌套跨 2 个音"（用户报的"2 个都是跨 2 个字符"）。
   - **渲染**：`_slur_chains()` 把相邻对拼回一条弧，`_draw_slurs()` 画正弦拱；

     > （与音区点同一档；被包含的判据是起止都落在自己区间内，**共用端点也算**）。
     **数字谱图与 MusicXML 两条路径都画**。

9. **重音记号 `>`（已补上）**。原谱画在音符正上方，是一个尖朝右的小 V。
   此前图片路径**完全不识别**这类"上方记号"（`>`/`v`/`³`/房子标号全丢）。
   现已支持 `>`：
   - **判据全部来自实测**（《上海滩》第 1 行 6 个 `>`，ASCII 形状图确认尖朝右）：
     `宽 0.82~0.85H、高 0.64H、填充 0.27~0.28、拱起 0.09~0.19`。
   - **区分其它上方记号靠三个量交叉**，不是单一阈值（实测）：
     ```
     >           0.82~0.85H  填充 0.27~0.28  拱起 0.09~0.19
     v  (换气)   0.45H       0.31           0.80      ← 宽度 + 拱起双重排除
     小 2(房子)  0.53H       0.29           0.90      ← 宽度 + 拱起排除
     ³  (三连音) 0.45H       0.49           0.21      ← 宽度排除

     连音弧      ≥1.6H       0.17~0.19      0.82+     ← 宽度 + 拱起排除

     **所以不需要判"尖朝右还是朝下"**——`v` 在尺寸与拱起上都进不来。
     （本来以为必须靠方向区分，看了 ASCII 形状才发现不用。）

     `note["accent"]`（OCR 检测）→ 审核 JSON **存也读** → 字母谱 XML（`note_text` 追加 `>`）
     → 逐行文本（`note_to_token` 追加 `>`；`_TOKEN_RE` 已加 `(>*)` 组，可往返）

     → `letter_render` 也画

     **排版规则**说的，新增记号不涉及排版）。

   > 要做时照 `>` 这条链加字段即可。
10. **`v` 换气 / `³` 三连音 / 房子标号 `1.2.3.`（已补上，阈值暂定）**。
    这三者与 `>` 都属于"数字上方的小记号"，检测共用一个思路：**先按尺寸圈定"小记号"，
    再用两个有物理意义的量交叉分辨**。
    - **分辨依据**（实测）：
      ```
      v  (换气)   0.45H  拱起 0.80  底部横杠 ≈0.2   ← 两笔收成**尖**
      ³  (三连音) 0.45H  拱起 0.21  底部横杠  —      ← 笔画偏竖直
      房子标号     0.53H  拱起 0.90  底部横杠 ≈1.0   ← 小**数字**，有满宽基线
      ```
      所以：`拱起高 + 底部是尖` → `v`；`拱起低` → `³`；`底部有基线` 或 `旁边有房子括线`
      → 房子标号。**分支顺序有讲究**：`v` 必须先判，否则会被房子标号抢走
      （两者拱起都高：0.80 vs 0.90，光看拱起分不开）。
    - **`³` 与房子标号 `3.` 是同一个字形**（都是小 3），字形上无法区分 →
      只能靠 `_near_wide_bracket()` 判断"旁边有没有那条 ≥6H 宽的房子括线"——
      **这是唯一依据**。
    - **链路**：`note["breath"]` / `note["triplet"]` / `note["house"]`（OCR 检测，挂在最近的音上）
      → 审核 JSON **存也读** → 字母谱 XML（`note_text` 追加 `,` / `t` / `[n]`）
      → `jianpu_render._draw_upper_marks()` 画在数字上方（四种记号合并成一个函数，
      同音多个记号会往上叠）→ `letter_render` 也画。
    - ⚠ **阈值是"暂定"**：每个记号只从《上海滩》取到 **1 个样本**（`v` 1 个、`³` 1 个、
      房子标号 1 个）。分不清的一律**不标**（宁缺勿假），`VERBOSE_DEBUG` 下会打
      `[mark?] … 分不清，跳过`。诊断里带了 `底杠` 与 `房线` 两个新量，跑一遍就能定准。
    - ⚠ **踩到的坑：上一行的数字会掉进"数字上方"的窗口里（已修）**。搜索窗口照抄了

    - **窗口下界**取「**下一行数字的顶部**」（末行兜底 `+8H`），**不是固定的 `3.5H`** ——
      实测段间距 ≈2.1H、行间距只有 ≈5.7H：要够到第 2 段（+4.0H）就得放宽，而放宽到 5.7H
      就会把**下一行的歌词**卷进来当成第 2 段（第一版就是这么错的）。用下一行顶部当界，换谱不用调数。
    - **切成“音节槽”**：汉字/字母/数字各起一槽，**标点并入相邻槽**（`_LYRIC_PUNCT`，用户 2026-09-30 指出）。
      标点不该独占一个音的时值；更关键的是 —— **槽数相等才是三段词能互相对齐的前提**，
      而“字数”会因标点多少而不同（实测《上海滩》三段是 13/12/14 字）。槽按 `x` 排序后，
      **按槽的 `x` 就近**分配到音符（原谱规则就是“同一个音节在同一个 x”，所以三段天然对齐，
      哪怕各段槽数不同）。
    - **丢弃门槛挂在“本行的音距”上**（`[首音 − 中位音距, 末音 + 中位音距]` 之外才丢），
      **不是固定的 1.3 字高** —— 旧绝对门槛实测让《上海滩》丢了 5 个字（距离 1.37~1.72H，刚过线）。
      （当日第 N 次踩同一个坑：**绝对阈值换谱就碎**。）
    - ⚠ **残余**：少数图会聚出**只有 1~4 个字**的 `lyric2`/`lyric3`（重跑 1–20 后只有 16.jpg 是这样），
      疑似误分段，核对时留意 —— 真正的第 2 段通常几十个字起（如 11.png 142 字）。上游 `text_tokens` 的**跨尺度去重**见第 6 条。
15. **假休止复核：判成 `0` 的音里挑出被误判成休止的数字（2026-09-29 重做）**。
    用户 2026-09-21 报“6 被标记成 0 无法识别”，2026-09-29 拿 **43.jpg / 51.png** 两个具体案例要求重做。
    判据**取并集**（任一成立就改判）：
    1. **原有**（保留）：形状分 ≥ `FAKE_REST_MIN_SCORE`（0.75）→ 高分场景可靠。实测 7.png 两块、
       14.jpg 一块、22.jpg 一块靠它修对。⚠ 2026-09-29 第一次重写时**误把它删掉**，
       那 4 块立刻退回 `0`（全库 A/B 抓到）—— 所以它必须留着。
    2. **新增**：**孔比离群地小** —— 本块孔比 < `FAKE_REST_HOLE_FACTOR`（0.7）× 本图**其它** 0 块孔比的最小值。
       `0` 必须有明显封闭内孔，孔比离群地小就不是 `0`。过了这关再问“最像谁”（`_reference_scores`，**不设门槛**）：
       argmax ≠ 0 → 改判它；argmax = 0 但与 `6` 差 < `FAKE_REST_TIE` → 改判 `6`。
    - ⚠ **已知缺陷 —— 失效方向是"整张图查不出来"，不是"把真 `0` 改错"**：基准取"最小值"意味着
      **只要图里有一个孔比 = `0` 的 0 值块**（实心椭圆休止符的字体、或 `_hole_class` 给不出明细的碎块），
      基准就被钉成 `0` → `ratio < 0` 恒假 → **判据②在这张图上整体失效**（2026-09-30 实测复现：
      7.png 的 box=(1065,917) 正是这样一个块；该图那两个假 `6` 当时是被 ① 救回的，所以输出没露出来）。
      正解：基准改取"**次小值**"、或先把 `0` 排除在基准之外。
    - **为什么必须补 ②**：43.jpg 那个真 `6` 的形状 `6`=0.671 vs `0`=0.657（**余量 0.014**）、
      51.png 的是 0.677 vs 0.674（**余量 0.003**），都卡在分类器的 `min_margin=0.03` 里返回 None，
      且绝对分够不着 0.75 —— ①在那类**小字号扫描件**上永远失效（那类图形状分整体只有 0.5~0.55）。
    - ⚠ 第 ② 条**不能省“孔比”这第一步**：实测只看 argmax 会把 10 个（孔比 0.211~0.235 的）真 `0`
      改成 `1`/`6`，它们的 argmax 领先幅度只有 0.008~0.031，纯属噪声。
    - **基准用本图自己的最小值、不用固定阈值**：孔比受字号/字重影响极大（42/45 的真 0 是 0.211~0.235、
      51 的降到 0.113），固定阈值换谱就碎（这条路已栽过两次）。
    - **实施顺序**：必须放在 **0/6 复核之后** —— 那一步正是把 14.jpg 行1 那个真 6 改成 0 的元凶。
      改判过的块打 `_from_fake_rest` 标记，让后面的「5/6 复核」**让路**
      （两条规则从同一份孔比证据推出相反结论：这里判“不是 0 → 是 6”，5/6 复核判“标为 6 却没内孔 → 是 5”；
      51.png 那块是 `6`）。全库 51 张：孔比可疑块仅 3 个，并集后**净增改判 2 个** —— 恰好是 43/51 那两个真 `6`。
